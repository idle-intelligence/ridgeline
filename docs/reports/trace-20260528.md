## Progressive Slowdown — Confirmed

Frame time grows monotonically for ~40 s, then partially recovers:

| Trace window | Frames | Mean frame time | Median frame time |
|---|---|---|---|
| t = 0–10 s | 234 | 42 ms | 57 ms |
| t = 10–20 s | 168 | 59 ms | 72 ms |
| t = 20–30 s | 123 | 82 ms | 96 ms |
| t = 30–40 s | 68 | 146 ms | 155 ms |
| t = 40–50 s | 49 | **208 ms** | 248 ms |
| t = 50–60 s | 52 | 188 ms | 230 ms |
| t = 60–67 s | 45 | 154 ms | 196 ms |

The WASM step fraction remains **83–88% throughout** — meaning the slowdown is driven purely by the WASM step doing more work per frame, not by any change in JS overhead.

`bufferSubData` cost tracks the same curve (0.13 ms/frame at t=0–10 s → 3.64 ms/frame at t=40–50 s → 0.65 ms/frame at t=60–70 s), confirming the visible geometry set (vertex/index data uploaded each frame) grows then shrinks — consistent with the camera climbing to a high altitude that expands the visible terrain footprint, then descending.

**JS heap is stable throughout (6–8 MB), so the slowdown is not a JS memory leak.** No WASM memory growth events are in the trace. The growth is behavioral: more terrain strips visible = more geometry generated by `eng.step()` each frame.

## Top 3 Costs

1. **WASM `eng.step()` — 90 ms/frame avg, 99% of frame time.** The entire frame budget is consumed by Rust geometry generation. The five heaviest WASM functions (`fn[20]`, `fn[50]`, `fn[24]`, `fn[23]`, `fn[12]`) account for ~83 ms of that at peak. `fn[24]` shows the steepest scaling with visible strip count (6.2× growth).

2. **Progressive geometry growth — frame time 4.9× from start to peak (42 ms → 208 ms).** Not a memory leak. Driven by the camera reaching high altitude / wide view, expanding the number of terrain strips generated per frame. WASM step and `bufferSubData` both scale proportionally. This is the same phenomenon regardless of whether the memory fix landed — the trace predates no such information, but JS heap is stable so the fix (if it addressed JS leaks) would not change this curve.

3. **`bufferSubData` — 1.1 ms avg, peaks at 3.6 ms/frame at high altitude.** Proportionally small (< 5% even at peak), but it confirms large geometry arrays are uploaded every frame. Both vertex and index data for fill + line geometry.

## What the Trace Does NOT Show

- **Rust function names** — no WASM source map in the trace. `wasm-function[20]`, `[50]`, `[24]`, `[23]` are the index positions in the binary; the actual Rust function names require a `.dwarf`/DWARF section or `wasm-pack`'s name section. Build with `wasm-pack build --dev` or `RUSTFLAGS="-C debuginfo=2"` and re-record to get names.
- **Which specific geometry operation inside `fn[24]` causes the 6.2× scaling** — the profiler can't see inside a single WASM function body.
- **Whether the "memory fix" described by the user is relevant here** — JS heap is stable (6–8 MB, no growth), so whatever fix landed, it does not address the dominant per-frame WASM work or the geometry-count growth.
- **GPU shader-compile costs** — no compile spike visible; shaders are compiled before the trace starts. Confirming via `chrome://gpu` would be needed if that were a hypothesis.
